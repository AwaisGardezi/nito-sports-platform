## 2026-10-09 — Session 14: one staff account, no create-account anywhere

### The request
Awais: *"Make the Platform Like That Only Staff Have One Account There Should be No Create
Account On Staff Login."*

He was right to ask. `login.html` offered a **"Create account" tab**, and `platform.js`'s
`signUp` made **the first account the owner**. On a browser with no account yet — a fresh
visitor, a cleared cache, a new device — that meant anyone who found `/login.html` could
register and own the console. It was open registration wearing an enterprise costume.

### The design decision (do not re-litigate)
**A single staff account, created once, then closed.** The rule is enforced in **two
independent places**, because either alone is not enough:

1. **The UI** — `login.html` has no registration affordance at all. The `auth__tabs` block
   and both `#tabIn`/`#tabUp` buttons are gone, and the `?mode=signup` deep link with them.
2. **The API** — `LocalAdapter.signUp` rejects outright once `_users().length > 0`. A UI-only
   fix is cosmetic: the page can be edited in devtools or the method called from the console.
   **Only the API guard makes the rule real.**

**One-time setup is not a loophole.** A console with zero accounts is unreachable, so the
first run asks once for the owner's details and then never again. `login.html` picks between
the two states by asking `NitoPlatform.hasAccounts()` and publishes the answer on
`#authForm[data-mode]` — `"setup"` or `"signin"`. The steady state is always `signin`.

Rejected alternative: seeding the owner's e-mail + password from `catalog.js`. That file is
**publicly served** on a static host, so it would have published the admin password to anyone
who viewed source — a worse hole than the one being closed. The password is chosen in the
browser and stored hashed.

### Files changed
- `assets/js/platform.js` — `hasAccounts()` on `LocalAdapter` (resolve `_users().length > 0`),
  `CloudAdapter` (always `true` — never offer setup on a shared deployment) and the facade;
  `signUp` guarded; `seed().settings.allowSignup` → `false`.
- `assets/js/auth-page.js` — rewritten. Two modes collapsed into one `setup` boolean set once
  in `boot()`. `apply()` paints either state; `note()` is setup-aware. On any error
  `hasAccounts()` failure defaults to **true** (assume set up) — offering setup when it is not
  wanted is the riskier of the two failures.
- `login.html` — tabs removed, copy rewritten, `data-mode="signin"` on the form.
- `tests/staff-login-test.js` — **NEW, 18 checks.**
- `run-tests.sh` — now **15 suites**.
- Retargeted: `admin-test.js`, `console-test.js`, `export-test.js`, `console-ui-test.js`,
  `product-images-test.js`, `enquiry-pipeline-test.js`.

### The dead-branch bug the retarget exposed
The `signIn()` helper in three suites had an `else` branch setting `#iEmail`/`#iPass` — **ids
that do not exist on `login.html`**. `set()` silently no-ops on a null element, so that branch
would have submitted an empty form. It never ran because every suite uses a fresh
`userDataDir`, so `fresh` was always true. Fixed to `#aEmail`/`#aPass` while retargeting.

### Sabotage proof
Restoring the old `role: first ? 'owner' : 'viewer'` (multiple accounts allowed) turned
**exactly two** checks red — "a second staff account is refused" (`accepted`) and "the refused
attempt added nobody". Guard restored, `grep -c "first ? 'owner' : 'viewer'"` → **0**. The
sabotage also exposed that the second check printed `undefined` instead of a count; it now
reports `users=N`.

### Honest limit, asserted rather than hidden
On the **local adapter**, clearing browser data removes the account and re-offers setup. That
adapter is explicitly not a security boundary — which is exactly why the hosted backend must
be bound before real use. `staff-login-test.js` asserts this with a `KNOWN LIMIT` label so the
property is *known* rather than discovered later.

## 2026-10-09 — Session 14e: forgot-password removed; a DANGEROUS advice bug fixed

Awais: *"I forgot Staff Login Credentials"*, then *"Remove Forget Password From Staff Login"*.

### The bug this uncovered — the old advice would have destroyed his catalogue
`forgot()` told the operator to *"clear this site's browser data to reset your local password —
your product data is stored separately and is not affected."* **The second half was false.** Chrome's
"delete cookies and other site data" clears **all** localStorage for the origin, including
`nito_platform_v1` — the ~51 KB catalogue — and the `nito_med_*` photo keys. Following the app's own
advice would have wiped the products and photos while promising they were safe. This was live for
several sessions and no test covered prose.

**The truth it should have told:** the account key (`nito_platform_users_v1`) *is* separate from the
catalogue key (`nito_platform_v1`), so removing **only** the account + session keys re-offers the
one-time setup and keeps everything else. That is a narrow, safe operation — and it is what the
replacement does.

### What changed
- **`#resetBtn` "Reset console access"** added — the single recovery route. Confirms first (a dialog
  naming exactly what is and is not removed), then deletes only `nito_platform_users_v1` +
  `nito_platform_session_v1` from **both** localStorage and sessionStorage, then reloads. Shown only
  on the **local adapter** and only when an account exists, so it vanishes once the backend is bound
  and real recovery exists.
- **`#forgotBtn` removed** on the owner's instruction, along with `forgot()` and its binding — it
  promised a reset that cannot exist without a backend.

### Two test mistakes worth remembering
1. My first guard asserted the message contains no `clear site data`. It failed — because the **new**
   copy *names* "clear site data" in order to **forbid** it. A negative regex on a word cannot
   distinguish "do this" from "do not do this". The assertion was rewritten to test the
   **instruction** (`/do not use your browser/i` present, `/clear this site/i` absent).
2. A project-wide grep for `forgotBtn` did **not** return the hit inside `tests/staff-login-test.js`,
   so I nearly shipped a test that clicked a deleted button. A follow-up grep scoped to
   `tests/` found it. **Grep the suite directory explicitly when removing a selector.**

## One-click launch — "a single button execution" (the owner's ask)

> *"Make me a single Click button Like I'll Press and The Platform Will be Hosted Locally and Will be
> Executed With the Connected Frontend and Backend. Make me a Single button Execution."*

**Delivered: `Start NITO Platform.cmd`** (Windows) and **`start-platform.sh`** (macOS/Linux). One
double-click starts a real HTTP server, serves the public site **and** the console **and** an API on one
URL, and opens it. ASCII-only `.cmd`, `cd /d "%~dp0"`, three Node lookup tiers, and `pause` on error so
a failure is readable instead of a window that vanishes.

### The backend behind it — `tools/server.js`

Zero-dependency Node (~470 lines), because the brief allows no build step and no framework.
- **Durable storage** in `data/platform-db.json` — atomic tmp+rename, so a crash mid-write cannot
  truncate the catalogue.
- **Real auth** — `crypto.scryptSync` with a per-user salt and `timingSafeEqual` comparison;
  server-side sessions in an HttpOnly `nito_sid` cookie.
- **"One staff account, no self sign-up" is enforced ON THE SERVER** — a second `/api/auth/signup`
  gets **403**. This is the first time that rule has a real boundary rather than a UI guard.
- Seeded from `assets/js/catalog.js` via `new Function('window', src)(win)`, so the API starts with the
  genuine 55-product catalogue, not a fixture.

### Wiring the frontend to it

Three new files: `assets/js/cloud-shim.js` (a `fetch`-backed `NitoCloud` client against same-origin
`/api/`), `assets/js/cloud-config.js` (**only sets the config on localhost/127.0.0.1/::1** so a deployed
copy never points at a visitor's own machine), and the dev server's HTML injection — a static host
cannot inject scripts, so `tools/server.js` injects those three scripts into served HTML, marked with
`<!-- nito-backend-injected: dev server only -->`.

**Two honesty bugs fixed in `platform.js` on the way:**
1. `CloudAdapter.ready()` had a `.catch` that swallowed the probe failure and returned `info()` — so an
   unreachable backend reported **"Hosted (shared)"** while every read and write went nowhere. Removed;
   `init()` now falls back to `LocalAdapter` with a visible `bootError`.
2. `hasAccounts()` was hardcoded `Promise.resolve(true)`. That added no security and broke a fresh
   backend the owner legitimately owns (a sign-in form, no account, no way to make one). It now **asks**
   the backend, defaulting to `true` only on error — the safer failure.

## Two honesty gaps found while screenshotting the launcher

Taking proof shots of the running platform surfaced two claims on `login.html` that the code does not
back. Both were fixed, and the second is a real functional gap the owner needs to know about.

1. **"Add a product and it is live on the site — no export step."** True while the platform is running
   (the bridge arms and the site reads the API), false on a static host where the public pages read the
   frozen `catalog.js`. Now scoped: *"With the platform running, a published product is live on the
   site — no export step."*

2. **"Every quote request lands in one inbox you can work through."** **This was false, and not just in
   wording.** `enquiries.js` records into `localStorage` (`nito_enquiry_queue_v1`), which is **per
   browser**. A buyer on another machine writes to *their own* store, which the owner's console can
   never drain. So the console inbox is only ever populated by submissions made **in the browser that
   runs the console** — i.e. the owner's own testing. What actually delivers a real visitor's enquiry
   today is **WhatsApp** (and e-mail once `formEndpoint` is set), never the inbox.
   Rewritten to what is true: *"Every quote request is recorded the moment it is sent, then delivered
   by WhatsApp — a blocked popup cannot lose it."*
   **The fix for the underlying gap is now cheap** because the local backend exists: `enquiries.js`
   should POST to the backend when the platform is shared. Logged at the top of the roadmap.

Recorded in `MEMORY.md` as a `KNOWN GAP` so no future session re-adds the "one inbox" claim, and so the
console inbox is not mistaken for a working surface until it is wired.
