## Session 2 — "Real 100% working Platform / copy the frontend from shazamindustries.com"

### What the reference site actually is
Fetched and analysed `shazamindustries.com` raw markup + CSS. It is a classic **PHP + jQuery/Bootstrap
catalog site**: `index.php`, `products.php?live=`, `detail.php?live=`, `content.php?p=`, `basket.php`.
Frontend feature set = hero banner carousel (4 banners), category image grid, product grid with
**product codes** (SI-xxxx), trust badge strip (Best Price / Best Quality / Fastest Shipping / Custom
Label), newsletter subscribe, social follow, multi-column footer, enquiry **basket**.
Its visual identity is **white bg + gold `#f9b20a` accent + dark header** (fonts PT Sans / Poppins).

### Decision taken (asked the user, they chose)
- **Design: keep NITO dark premium** (dark navy/black + NITO blue), NOT Shazam's white/gold.
  "Copy the frontend" was interpreted as *copy the feature set and layout structure*, not the colours.
- **Platform depth: static + real admin**, hosted free on Cloudflare Pages. No backend/database.
- Explicitly did NOT clone Shazam's markup, copy or images (copyright + credibility risk if buyers
  compare the two sites). Rebuilt equivalent features under NITO branding.

## Late addition — documented the "add a product" workflow and proved it works

Awais asked how to add products "like on the reference site". Investigated the reference site:
it sets a `PHPSESSID` cookie and has no public admin link, i.e. **PHP + MySQL** — products are
database rows, so adding one is instantly live. Ours is static, so the cycle is
**edit → export catalog.js → upload**. That difference is now explained up front in the guide so it
doesn't read as a missing feature.

- Rewrote `HOSTING-GUIDE.md` §4 into a full walkthrough: comparison table (panel vs hand-editing),
  why the export step exists, numbered steps, a **field-by-field reference** for all 16 product
  fields, the 24 garment-drawing keys, how the sidebar sub-range is derived, a worked example
  (Cricket Sweater), the other panel buttons, upload methods, and a hand-editing schema block with a
  comma warning.
- Documented the sub-range rule and verified it: the sub-range comes from **word-matching the product
  NAME** against `category.items`. `Cricket Sweater` → Cricket, `Basketball Jersey` → Basketball,
  `Yoga Leggings` → Leggings, an unmatched name falls back to `items[0]` (Football / Soccer for
  teamwear). Override with `window.NITO_SUBCAT_OVERRIDES`. Caveat found: `Gym Hoodie` → **Gym T-Shirts**
  because the word "gym" wins — worth knowing when naming products.
- New test `tests/add-product-test.js` proves the whole loop: panel 55 → add → export
  (60,548 bytes) → swap in as the live `catalog.js` → `products.html` reports **56 product lines** →
  `?cat=teamwear&sub=Cricket` shows the new card under Cricket → search finds it → 0 page errors.
  Original restored (55 products, `NTO-1016` absent), smoke test still ALL PASSED.

**Gotcha confirmed:** after uploading a new `catalog.js` the browser serves the cached old file — the
test only passed once `setCacheEnabled(false)` was used. This is exactly why the guide insists on a
hard refresh (`Ctrl`+`F5`). Real-world equivalent: Cloudflare's edge cache may also need purging.

## Late addition — order reference number in the WhatsApp handoff

Awais asked that everything a buyer types into the enquiry form be carried to WhatsApp "with the
order no". The form already forwarded all 12 fields; the missing piece was a reference number.

- Added `makeRef()` in `site.js` → `NTO-YYMMDD-NNNN` (e.g. `NTO-261007-4821`): readable aloud,
  sortable by date, four random digits. Deliberately documented as a **reference, not a database
  ID** — the digits are random so same-day collisions are theoretically possible.
- Rewrote `buildText(ref)` to lead with `*NEW ENQUIRY — NITO SPORTS*` / `*Order ref: …*` and to use
  **WhatsApp bold** (single asterisks) plus sectioned blocks: Buyer / Product required / Quote list /
  Order details / Customization / Message / Reference files. The files block now only appears when
  files exist (it used to print "none").
- The reference is also injected into the **e-mail subject** (`[NTO-…] Quotation request — …`), the
  optional Web3Forms payload (`reference:`), and rendered on screen as a `.ref-chip` (dark chip, gold
  mono text, `user-select:all` so one click copies it).
- **Double-submit guard:** the built message with the ref replaced by `{REF}` is compared against
  `form.dataset.lastBody`. Identical content reuses the previous reference instead of issuing a
  second enquiry number; changing any field issues a new one. Verified both ways.
- Fixed a latent bug found while testing: `status.scrollIntoView(...)` threw in jsdom (and would throw
  in old browsers). Added a guarded `scrollIntoViewSafe()` helper and routed both call sites through
  it. Named it that way on purpose — an earlier draft called it `scrollTo`, which shadowed
  `window.scrollTo` inside the IIFE.
- New suite `tests/enquiry-test.js` (39 checks) intercepts `window.open`, decodes the
  generated `wa.me` URL and asserts every field is present, the reference matches `NTO-\d{6}-\d{4}`
  with today's date, the on-screen chip matches, WhatsApp bold markers are used, the quote-list block
  and product codes come through, and each enquiry gets its own reference. Smoke test also gained an
  enquiry assertion, so this is regression-protected.
