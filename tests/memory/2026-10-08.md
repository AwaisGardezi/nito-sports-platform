| - | --- | ---------- | --- |
| 1 | **Sidebar navigation did nothing** | `parseHash()` read `location.hash` back after assigning it. | 6 | **Audit log couldn't name the actor** | `log()` never recorded the role; the table rendered only the display name. | Added `actorRole`; row shows display name + email + role badge. |

Plus an a11y gap: the enquiry "Open" button had no accessible name.

### jsdom gotcha that wasted the most time: **navigation is unobservable**
`window.location` exposes `replace`, `assign` and `href` as **own, non-writable, non-configurable
properties on the instance**; `Location.prototype` has none of them. Therefore:
- patching the prototype → silent no-op
- patching the instance → silent no-op (`writable=false`)
- `Object.defineProperty` → throws `Cannot redefine property`

So no redirect can be intercepted. `probe-location.js` proves it. **Assert on product-visible state
instead** (session really gone, shell really hidden) — not on navigation. Also: jsdom fires
`Not implemented: navigation to another Document` for a redirect you *asked* for; filter exactly
that string, don't blanket-silence.

### Other harness notes
- Pages render **asynchronously** (every page reads the platform first), so a fixed sleep is a race.
  Added `settle(fn, timeout)` polling.
- Share one `localStorage`/`sessionStorage` backing map across JSDOM instances — that is what makes
  the "survives reload" check a real persistence test rather than a same-object check.
- Viewer role sees **6** sections, not 5: `settings` is `perm:'read'` so only Team and Audit hide.
- The role matrix lives on `#view`, not inside `#tBody`.
- Seed enquiries through `NitoPlatform.create(...)`, not by writing localStorage directly — doing it
  the short way is what *hid* bug #2.

## Session 4 — "go further": publish-to-website, and a proxy trap

### The proxy trap (cost the most time, will bite again)
This shell sets `http_proxy`/`https_proxy=http://127.0.0.1:21005` but **does not set `no_proxy`**.
So *every* request to `127.0.0.1` was routed **through the proxy**, which cannot reach loopback and
answers **502**. Consequences:
- the readiness probe in `run-tests.sh` saw a "successful" response on 8099, concluded a server was
  already up, and never started one → **8 of 9 suites died** with an opaque `CdpFrame.goto` stack
  that looked like a code bug
- `Bash` calls kept failing with `sandbox-center` errors

Both halves are now fixed in `run-tests.sh`:
1. `export no_proxy="127.0.0.1,localhost,::1"` (and `NO_PROXY`), and unset the four proxy vars.
2. `server_up()` probes `index.html` with `--noproxy '*'` and requires **HTTP 200** — not merely
   "something answered the port". It also now fails loudly with exit 2 and a real explanation.

**Diagnostic that found it:** `curl -s -o /dev/null -w '%{http_code}'` → `502` from a *proxy*, not
`000` from a dead port. `000` = nothing listening (correct); `502` = a proxy is in the way.

### The gap that mattered: admin edits did not reach customers
Awais said the admin content must "show to the customers". It did not. Two systems existed:

| | old `admin.js` panel | new console |
|---|---|---|
| Writes | → localStorage | → localStorage / cloud |
| Publishes | **exports `catalog.js` you upload** | nothing — JSON backup only |

The old panel was the **only** path from an edit to the live site. The console's own Settings page
admitted this ("the public website still reads `assets/js/catalog.js`").

**Fix:** added `publishCatalog()` to `admin-pages.js` + a **Publish to website** button on the
products toolbar (hidden when the cloud adapter is live, because then saving publishes directly).
It exports the same `catalog.js` format the site loads — `NITO_SITE` + `NITO_PAYMENTS` +
`NITO_CATALOG` — and it:
- ships **only published** lines; drafts stay in the console
- **strips** `published` / `createdAt` / `updatedAt` (console bookkeeping, not site data)
- names the drawer count in the header comment
- writes an audit entry (`action: 'publish'`)

### Do NOT delete the old panel yet
`admin.html` was rewritten into the console shell, so `admin.js` + `admin.css` are now orphaned —
their `#admGate/#admPanel/#admList/#admNew/#admExport` markup no longer exists. That is why
`admin-test.js`, `export-test.js` and `add-product-test.js` fail. Those suites still encode the
`catalog.js` round-trip, which is genuinely valuable, so **retarget them at the console's Publish
button rather than deleting them.** Ownership call for Awais: either port what the old panel still
does uniquely, or retire it deliberately.

### New assertions (95 checks now, all green)
The publish test is an **acceptance** test, not a smoke test: it intercepts `URL.createObjectURL`,
captures the blob, then **executes the exported source in a clean sandbox** and asserts it re-parses
into 5 categories / 56 products with the new product present, `NITO_SITE`/`NITO_PAYMENTS` intact,
console-only fields stripped, and **no `price`/`retail`/`rrp`/`msrp` key** (the B2B no-pricing rule).
A download that only *looks* right is the classic way an exporter ships broken output.

## Session 7 — walking Awais through adding products (found a lying toast)

Awais asked how the admin adds products. Writing the walkthrough meant reading `saveProduct()`
properly, which surfaced a **real defect** in the success message:

```js
A.toast(isNew ? 'Product added — it is live on the site' : 'Changes saved and published');
```

On the local adapter that is **false**. Saving writes to this browser's `localStorage`; the public
pages keep reading the static `catalog.js` until the operator hits **Publish to website** and uploads
the file. The console already knows the difference — `P().mode().shared` is `false` for local and
`true` for cloud — and the products page already used it to *hide* the publish button. The toast just
never consulted it. Meanwhile the `modeBanner()` on every page says the opposite, so the UI
contradicted itself at the exact moment the operator was most likely to believe the wrong one.

**Cost if left:** Awais adds a product, reads "it is live on the site", tells a customer it is up —
and it isn't. Exactly the class of claim this project is not allowed to make.

**Fix:** branch the wording on `P().mode().shared` — "live on the site"/"saved and published" only
when the backend is genuinely shared, otherwise "saved in this browser — use *Publish to website* to
put it on the site". `admin-test.js` + `console-test.js` (95 checks) re-run green; no test depended on
the old string.

Lesson worth keeping: when a UI claims an outcome, **the claim has to be derived from the same fact
the rest of the system uses**, not written once and assumed.

### The two-step model to explain to the owner
1. **Save** → goes into the console's store (this browser today, the hosted DB once connected).
2. **Publish to website** → downloads `catalog.js`; uploading it over `assets/js/catalog.js` is what
   puts the product on `products.html`. Until then customers cannot see it.
Skipping step 2 is the single most likely mistake, which is why the toast now names it.

### The "No Child Labour" call — and why it is NOT a badge
SCCI and FBR are **verifiable third-party facts**. "No child labour" is a **self-assertion with no
issuing body**, so rendering it as a stamp beside two government marks would launder credibility it
has not earned — and sportswear supply chains are audited hardest exactly here. Written instead as
**stated policy in the owner's own words**: no workers under 18, units visited in person, floor open
to a buyer's audit. Stronger, because it names something checkable, and defensible if ever challenged.
If a real certification is obtained later (SEDEX/SMETA, buyer audit), swap in the badge then.

visible rather than hidden: an empty slot is honest, an invented number is not. Owner to-do.

covers all 9 pages. Labelled by audience, not mechanism, so buyers read it as not-for-them. Quiet
grey, gold on hover. `rel="nofollow"`.

### The float-collision bug (found only by hit-testing, not by measuring)
The WhatsApp float is `position:fixed` bottom-right; the copy bar is the last element on the page, so
**the float sat on top of the staff link and made it unclickable** — at 1440/1366/1280/1100px and
again at 600–760px.

Two wrong fixes before the right one, both worth remembering:
1. **Right-padding the bar** worked while the link sat on the right of a single row, and broke the
   moment the bar reflowed and the link moved left.
2. **Bottom-padding only below 900px** fixed the narrow band and broke desktop.

The right rule reasons about the float's **band**, not one axis: on a **single-row** bar reserve the
right edge (≥901px → `padding-right:200px`); on a **wrapped** bar reserve the bottom (≤900px →
`padding-bottom:84px`). Verified clean — no overlap, **clickable via `elementFromPoint`**, no
horizontal overflow — at **20 widths from 360 to 1920**.

**Lesson:** "no overlap" and "the user can click it" are different assertions. Geometry says the link
is 110px wide and visible; only `elementFromPoint` says nothing is painted over it. Test the second.

## Session 11 — "the dashboard opens but the frontend is not cool"

Awais's report was taste, so the job was to find what was *actually* wrong rather than restyle
on a hunch. Captured all 8 console screens first. Three real defects fell out.

### 1. Product name and description collided on one line (real bug)
`.tbl__name` is `display:flex`, but `.tbl__name-t` / `.tbl__name-s` were bare **inline spans**,
so they shared a line and the name's descenders ran into its own description — the table read
`3/4 Training PantsBelow-knee cut for lifting and field work.` on **every one of 55 rows**.
Fix: `display:block` on both, `min-width:0` on the wrapper so the text truncates instead of
forcing the column wide. Verified by **geometry**, not by eye: name 369–386, blurb 387–403.

### 2. The role matrix rendered metre-tall tick marks (real bug, worse)
`icon()` returns an inline SVG with a 24×24 viewBox and **no width/height attributes**. `app.css`
had `img,svg{display:block;max-width:100%}` and *every* icon context sized itself with a scoped
rule (`.btn svg`, `.side__link svg`, …) — except the team page's permission cells, which had none.
So the tick expanded to fill its `<td>`: 11 icons at 141–312px, and the Team page was 1965px tall.
The page looked **broken**, which is exactly what "not cool" meant.

Fix: a **default size in the design system** (`svg{width:24px;height:24px}`) so no future icon can
explode anywhere, with the existing scoped rules still overriding. Before/after: 11 oversized -> 0,
team page 1965px -> 985px.

### 3. Sparse pages were one card in a 1350px void
Enquiries / Customers / Categories / Audit / Settings each rendered a single small card floating
in dead space. Stretching it would only make a wide empty box, so those routes get `max: '1100px'`
(or 1180px) declared **in `ROUTES` next to their permission** — one choke point in `render()`, so a
new route cannot forget it. Dense pages (dashboard / products / team) stay full width.
- The cap applies to the **content children, not `#view`** — the store-mode banner must stay full
  width or it wraps mid-sentence. First attempt capped `#view` and did exactly that.
- Two wrong turns worth remembering: a `width:calc(100% + 0px)` "breakout" rule that did nothing,
  and asserting on `#view` instead of its children in the test.

### The visual depth pass
The console read flat because page and card were both ~`--ink-800` and the 3px stat rail was
invisible against its own card. Depth now comes from three cheap cues, not a shadow-heavy rewrite:
a **darker page plane** (`--plane` vs `--surface`), **1px inner highlight** on each surface, and
**one accent colour used sparingly**. Stat cards gained corner glows (colour-coded per stat) and
equal heights; empty-state icons became blue focal points; primary buttons got a subtle lift.
Hover transforms are wrapped in `@media (hover:hover)` so touch devices don't get a sticky card.

### New suite: `console-ui-test.js` — 45 checks
Every functional suite passed while the team page looked broken. **Geometry is not covered by
functional tests**, so this suite asserts on it: no icon >70px (excluding legitimately large

## Session 12: product image upload

Awais: *"Hey Like Make it Like I can Upload Product Images Too"*. `site.js` already rendered
`p.images[0]` (with a comment saying so) but nothing ever wrote it — the console had no image
field and `saveProduct()` emitted no `images` key. So the feature was half-built.

### The design constraint that shaped everything
`platform.js` keeps the **whole dataset in one localStorage key** (`nito_platform_v1`, ~51 KB)
and `_persist()` throws `'Could not save: browser storage is full.'` on quota. Putting a photo in
the product record means the next *unrelated* save — a MOQ edit, a draft toggle — re-serialises
the photos too and throws. Three or four photos would take the catalogue down with them.

So: **new module `assets/js/media.js`.** Image bytes live in their own keys
(`nito_med_<id>` full, `nito_medsm_<id>` ≤420px thumb) behind an index (`nito_media_index_v1`).
A product carries only `images: ['nito-media:<id>']` (~80 bytes) plus `imagePaths` (id → data URL
for what has been published). Client-side canvas downscale (1400px/0.82 full, 420px/0.72 thumb),
white background fill so a transparent PNG doesn't become a black JPEG, 3.5 MB budget guard
checked *before* writing, 25 MB input cap.

### The contract that would have shipped broken
`publishCatalog()` exports a standalone `catalog.js` with **no sidecar folder**. A `nito-media:`
ref in that file reaches the live site as a **broken image box**. So the export now calls
`resolveFull()` and inlines the **thumbnail** as a data URL (not the 1400px original — that keeps
the file ~10× smaller and the grid only ever renders it at ~280px). `imagePaths` is deleted from
the export. Unresolvable refs are counted and reported in a toast rather than silently dropped,
and a >900 KB export warns that upload will be slow.

### Two real bugs I introduced and caught
1. **`global` is not defined in a browser.** I wrote `global.NitoMedia` in `site.js`, which works
   in Node and throws `ReferenceError` in the page — the product grid was dead. Now `window.`.
2. **`paths is not defined`.** A partial edit left `var paths = ...` inside the block I replaced,
   so `commitImages()` threw and nothing ever saved. Caught by instrumenting `NitoPlatform.update`.

### New suite: `tests/product-images-test.js` (24 checks)
Builds a real PNG in-process (no fixture a cleanup could delete), drives the **real file input**,
and checks four contracts: PICK, STORE, PUBLISH, RENDER.

**Sabotage-proved three ways:** (1) export stops resolving → 3 red; (2) full data URL written into
the product record → 1 red; (3) `resolve()` stops reading stored bytes → 9 red.

**The fourth sabotage found a hole in my own suite.** Breaking the *grid's* resolver
(`NitoMedia.resolve(...)` → `refOf(p)`) turned **nothing** red — because the exported file holds a
plain `data:` URL, so every consumer works by accident and the resolver is never exercised. Added
a check for the only data shape that does exercise it: a product whose `images` is a raw
`nito-media:` ref, which is what `live-data.js` overlays once a backend is bound. Re-sabotaged
`resolve()` → 9 red including that check. *A guard that cannot fail guards nothing.*

### Also fixed
`console-test.js` keeps its script list as a hand-maintained literal that did not include
`media.js`, so the jsdom run threw `Cannot read properties of undefined (reading 'used')`.
Added it to both lists with a comment to keep them in step with the HTML, and made the capacity
meter defensive (a cosmetic readout must not throw).

### Status
**13/13 suites green** (was 12), `catalog.js` verified `b53176fd`, no page errors.
`export-test` timed out once in a back-to-back run (navigation, 13 browser suites on one machine)
and passed standalone — a load flake, not a product defect.

## Session 13: enquiries are captured, imported and quotable

Awais: *"Make Advancements... Everything in the platform Should be Real and Working Like a
Working Backend and Enquiry Should be Sent to Whatsapp"*. Asked which delivery model he wanted:
he chose **Save + WhatsApp + email**, and **build now / stay backend-ready**.

### The bug this fixed (and why it was the most expensive one on the site)
The contact form had exactly one outcome: `window.open(waLink(text))`. **Nothing was recorded
anywhere.** So a blocked popup, a closed tab, or a buyer who changed their mind produced the same
result as success — and the console inbox said *"No enquiries yet"* forever. Every other suite
passed; the site looked fine. A lead is the only thing this website actually produces, so this was
the highest-value defect left.

### Architecture: record first, deliver second
New **`assets/js/enquiries.js`** — an append-only queue (`nito_enquiry_queue_v1`).
- `site.js` submit handler now: **STEP 1** record locally → **STEP 2** email (if configured) →
  **STEP 3** open WhatsApp. Capture is step 1 precisely because a popup blocker cannot break it.
- The queue exists rather than writing straight into `nito_platform_v1` for two real reasons:
  (a) `LocalAdapter._sync()` re-reads that key, so a public-page write racing a console write can
  lose one; an append-only `push` cannot clobber. (b) `_persist()` throws on quota, and a throw in
  the capture path is exactly the lead loss being fixed.
- **`admin-shell.js`** drains the queue on boot *before* the first `refreshCounts()`, so the badge
  and inbox are already correct on the operator's first look. Also drains on the 15s poll, on tab
  visibility, and on the `storage` event — another tab's submit is the fastest honest signal.
- `enquiries.js` is handed a **writer function** by the console; it never touches the console's
  dataset. A lead whose import fails **stays queued** rather than being destroyed.
- Field names in the record match the console drawer exactly (`qty`/`sizes`/`deadline`/`custom`) —
  note the form's date input is `#f-date` but the record key is `deadline`.

### New: honest delivery reporting
The old email post was `fetch(...).catch(function () {})` — a 4xx read as success. Now
`NitoEnquiries.email()` treats a non-2xx as failure, has a 12s abort timeout, and the buyer's
confirmation panel lists **which channels actually fired** (`.form-status__ch`). If email failed,
the buyer is told, rather than being left to assume it went.

### New: the inbox is a working surface
`#qCsv` **Export CSV** — BOM (Excel + accented names), and formula-injection guarded (a cell
starting `= + - @` is prefixed with `'`, or a buyer's message starting "-" executes in the
operator's spreadsheet). The enquiries page also drains the queue on entry.

### A real crash I introduced and caught
`String($('#f-items', form).value)` — but `#f-items` exists **only on quote.html**. On the contact
page that threw `TypeError: Cannot read properties of null` and killed the submit handler, losing
the lead in the one place it was being captured. Caught because the suite drives the *real* form
rather than calling the handler.

### New suite: `tests/enquiry-pipeline-test.js` (26 checks)
Real contact page → real console, with a **stubbed `window.open`** so the popup-blocked case can be
tested directly. **Sabotage-proved three ways:** remove the capture step → 18 red; make a failed
import discard the lead → 1 red; disable the console drain → 4 red.

### Suite-list drift (second time)
`smoke-test.js` had a hand-maintained `SCRIPTS` list still missing `live-data.js` and `media.js`;
`console-test.js` needed `enquiries.js`. Both now carry a comment to keep them in step with the
HTML. This is the same trap that hid the `global`-in-browser bug last session.
